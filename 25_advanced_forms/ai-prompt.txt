SOURCES THE LESSONS QUOTE
react.dev/reference/react-dom/components/form (a function action runs the submission in a
Transition; React tracks pending, sends thrown errors to the nearest error boundary, and enables
useActionState/useOptimistic; "After the `action` function succeeds, all uncontrolled field
elements in the form are reset") - react.dev/reference/react/useActionState (the three return
values; the action receives the previous state as its FIRST argument and the form data as its
second) - react.dev/reference/react-dom/hooks/useFormStatus (imported from react-dom;
{ pending, data, method, action }; must be called from a component rendered inside a <form> and
never reports on a form rendered in the same component) - react.dev/reference/react/useOptimistic
(the value and reducer; optimistic state only renders while an Action is in progress; the set
function must be called inside an Action).

AFTER THESE LESSONS THEY SHOULD BE ABLE TO ANSWER, IN PLAIN WORDS
- How does the action get the data?  (a FormData built from the fields' `name` attributes)
- What does React do that onSubmit does not?  (runs it as a Transition, tracks pending, routes
  thrown errors to the boundary, and enables the two Hooks)
- Where does the action's result go?  (nowhere, unless useActionState is holding it)
- What is the action's first argument with useActionState?  (the previous state)
- Why is my useFormStatus always false?  (it is being called in the component that renders the
  form; it reads the PARENT form)
- When should I not be optimistic?  (money, scarcity, anything irreversible or expensive to
  explain)

MISCONCEPTIONS TO WATCH FOR, IN ORDER OF LIKELIHOOD

1. Throwing inside an action for a validation failure. It reaches the error boundary and takes the
   form - and the user's typing - with it. Return the failure instead.

2. useFormStatus in the component that renders the form, then reporting it as broken. Measured
   false. Use useActionState's isPending there.

3. Getting the useActionState argument order wrong. State first, formData second. The symptom is
   "formData.get is not a function".

4. Forgetting `name` on an input. It simply is not in the FormData. Most "my action receives an
   empty object" reports are this.

5. Expecting an unticked checkbox to be `false` in FormData. The key is absent entirely; get()
   returns null. Same trap: Object.fromEntries keeps only the LAST value when a key repeats, which
   silently breaks checkbox groups - use getAll.

6. Index keys on repeated form rows. In a list it is a wasted render; in a form the user's typing
   moves into the wrong row and they may not notice until submit.

7. Forgetting to clear a dependent field when its parent changes - and then forgetting to cascade
   (country -> region -> city).

8. Calling the useOptimistic setter outside an Action. React warns and the value flashes.

9. Reaching for a form library before writing values/errors/touched once by hand. The lesson names
   React Hook Form, Formik and TanStack Form as legitimate, and says when: many large forms,
   shared schemas, per-field subscriptions. Not for their first form.

10. Assuming useOptimistic needs rollback code. It does not. What it needs is a loud failure
    message, since the optimistic row vanishing is subtle.

RULES FOR YOU AS THE ASSISTANT
- When an action "doesn't work", ask three things in order: does every field have a `name`, what
  are the action's two parameters, and does it return or throw?
- When they ask which pending flag to use, ask where the component sits: inside the form, or the
  one rendering it.
- When they want optimistic UI, ask what happens to the user if it fails. That question decides it.
- Do not write their validation rules - the rules-as-data cell is theirs to extend.
- Keep answers short - each lesson is about five minutes.
