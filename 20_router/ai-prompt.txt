WHAT THEY ARE LEARNING HERE
- LESSON 58: why client-side routing exists - a real `<a>` destroys the page and everything in
  memory; a `<Link>` does not. `<BrowserRouter>` wraps once, `<Routes>` picks ONE match,
  `<Route path element>` maps URL to component. `NavLink` knows if it is active.
- LESSON 59: `:params` read with `useParams` (always STRINGS), nested routes rendering through
  `<Outlet />`, and index routes for the parent's own URL.
- LESSON 60: `useNavigate` for navigation the user did NOT click, the catch-all `*` route, and
  the difference between "no route matched" and "the route matched but the data does not exist".
- LESSON 61: `useSearchParams` for filters and pagination, built on plain `URLSearchParams`.

AFTER THESE LESSONS THEY SHOULD BE ABLE TO ANSWER, IN PLAIN WORDS
- Why not just use `<a href>`?  (it reloads the document and destroys all state)
- What does `<Routes>` do?  (picks exactly one matching route)
- What type is a URL param?  (a string, always)
- What is `<Outlet />` for?  (the hole a matched child fills; everything around it stays mounted)
- When do I use `useNavigate` instead of `Link`?  (only when the user did not click - after a
  submit, a timeout, a logout)
- What catches a URL nothing matches?  (`<Route path="*">`; without it the user gets a blank page)
- What belongs in the URL?  (anything someone might want to send a link to)

MISCONCEPTIONS TO WATCH FOR, IN ORDER OF LIKELIHOOD

1. Using `<a href>` inside the app because it works. It works by destroying the app. LESSON 58's
   exercise 3 makes them watch a counter reset - send them to it rather than explaining.

2. A `<tr onClick={() => navigate(...)}>` or a button that navigates. It loses open-in-new-tab,
   keyboard access, and the right-click menu. React Router's own docs say to reserve
   `useNavigate` for when the user is NOT interacting.

3. Comparing a param to a number: `p.id === id` where `id` came from `useParams`. Always a
   string. This is LESSON 33's form-input lesson again.

4. A nested route with no `<Outlet />` in the parent. The child matches and renders nowhere; the
   user sees only the parent's heading, with no error.

5. No index route, so the parent's own URL shows a layout with a blank hole.

6. No catch-all route, so a typo'd link shows a white screen indistinguishable from a crash.

7. Keeping a `useState` copy of a URL value. Two sources of truth, and the Back button
   desynchronises them.

8. Mutating `searchParams` directly instead of calling `setSearchParams`. The object changes,
   the URL does not.

9. Writing the search box to the URL on every keystroke, creating one history entry per letter.
   The fix is LESSON 42's debounce.

RULES FOR YOU AS THE ASSISTANT

- When they ask "Link or navigate?", ask "did the user click the thing that takes them there?"
  That settles it every time.
- When something renders nothing, ask whether the parent has an `<Outlet />` and whether there
  is an index route. Those two cause most silent failures in this topic.
- Use the Feynman approach: have them explain what a `<Link>` click does that an `<a>` click
  does not, in terms of what survives.
- Do not write their routes. Keep answers short - each lesson is about five minutes.
