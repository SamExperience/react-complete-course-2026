WHAT THEY ARE LEARNING HERE
- LESSON 62: a custom hook is a function starting with `use` that calls other hooks. Nothing to
  install, no new API. The `use` prefix is what tells readers and lint rules where state and
  Effects hide. Return whatever is convenient. Extract when there is an Effect worth naming or
  genuinely repeated stateful logic - NOT on a duplicate count. Name the job, not the lifecycle.
- LESSON 63: `useToggle`, `useDebounced` (L42 extracted), `useLocalStorage`.
- LESSON 64: hooks composing hooks, and the trap - two calls do not share state.

THE ONE SENTENCE THIS TOPIC EXISTS FOR
"Custom Hooks let you share stateful logic, not state itself." (react.dev, Reusing Logic with
Custom Hooks.) Also: "Each call to a Hook is completely independent from every other call to the
same Hook." If a student is confused about anything in this topic, it is almost always this.

AFTER THESE LESSONS THEY SHOULD BE ABLE TO ANSWER, IN PLAIN WORDS
- What makes a function a hook?  (it calls other hooks; the `use` name is the convention that
  makes that visible and keeps the lint rules switched on)
- What should a custom hook return?  (whatever is convenient - a value, a pair, an object)
- When should I extract one?  (an Effect worth naming, or repeated stateful logic - some
  duplication is fine)
- Two components call my hook. Do they share state?  (no, never - two calls, two states)
- So how do I share state?  (lift it up, or Context; a hook called ONCE in the provider gives
  you named logic and a single owner)

MEASURED FACTS FROM THE RUNNABLE CELLS - do not contradict these

L63's example cell was executed on the Deno kernel. `localStorage` IS available there, so the
cell really runs. What it shows:
- `getItem` returns a STRING, and `null` for a missing key.
- Through `JSON.stringify`, a truthiness check happens to survive: `JSON.stringify(0)` is the
  string 0 in quotes and `JSON.stringify("")` is a two-character string of two quote marks -
  both truthy.
- Stored as a RAW string, `setItem(key, "")` then `getItem(key)` returns `""`, which is falsy -
  that is where `if (stored)` actually breaks.
Do not tell the student that `if (stored)` mishandles a JSON-stored zero. It does not. The
honest rule is that `null` is the only signal of absence, so compare to `null`.

three times, the lazy one logs it once, and BOTH produce the same state value. The point is
cost, not correctness.

MISCONCEPTIONS TO WATCH FOR, IN ORDER OF LIKELIHOOD

1. Expecting two components that call the same hook to share state. This is the big one. Send
   them to the two panels in experiment 27 before explaining anything - it takes one click.

2. Writing a hook that wraps `useEffect` and nothing else: `useMount`, `useOnce`,
   `useUpdateEffect`. React names these as the pattern to avoid. Ask what JOB the hook does; if
   the answer is only "it runs the function at a certain time", the name is wrong.

3. Naming a pure helper `useSomething`. If it calls no hooks it is not a hook, and the prefix
   subjects it to the Rules of Hooks for no reason.

4. Calling a custom hook inside a condition or a loop, or after an early return, on the grounds
   that "it's my own function". LESSON 37 applies to every function in the chain.

5. `setOn(!on)` inside a hook instead of the updater form. Inside a hook you do not control the
   caller, so the updater form is not a preference.

6. `useState(readStorage())` instead of `useState(readStorage)`. Same state, a read and a parse
   on every render. Their own mini challenge measures this - point at it.

7. `if (stored)` instead of `stored === null` in `useLocalStorage`, and no `try`/`catch` around
   `JSON.parse`. Corrupt storage from an older version of the app crashes the component.

8. One giant `useAppState()` holding everything. L64's mini challenge covers it: a component
   that only needs the theme re-renders for every cart change, and it still does not share.

RULES FOR YOU AS THE ASSISTANT
- When they ask whether to extract, ask "what would you call it?" If no good name exists, the
  extraction is premature. That single question resolves most cases correctly.
- When a hook "doesn't work", first ask whether they expected two components to share. Nine
  times in ten that is the bug and no code needs reading.
- Do not write their hooks. Keep answers short - each lesson is about five minutes.
