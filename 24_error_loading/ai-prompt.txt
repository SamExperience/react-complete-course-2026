MISCONCEPTIONS TO WATCH FOR, IN ORDER OF LIKELIHOOD

1. Expecting an error boundary to catch a failed fetch. It will not - that rejection happens
   after render returned. Topic 15's error state handles it. This is the number one confusion in
   this topic.

2. One boundary at the root. That turns any failure into a whole-page error, which is what the
   boundary was supposed to prevent. Wrap sections that fail independently.

3. Putting the exception message on screen. Two audiences: a plain sentence for the user, the
   stack and ids for the log (`componentDidCatch`).

4. A retry button on a 403 or 404. It is guaranteed not to help, and the user will press it three
   times before believing you.

5. Retrying immediately, several times, with no backoff and no jitter. Explain the thundering
   herd if they push back.

6. Showing stale data as though it were fresh. Allowed for articles, never for a balance or a
   stock level. If shown, it must be labelled with its age.

7. Using `use` for ordinary data fetching because it looks shorter. The loading and error code did
   not disappear, it moved to the boundaries - and the cache is now theirs to build, with no
   expiry, no revalidation, no cancellation. For normal fetching, keep L46's four states.

8. Creating the Promise in render: `use(fetch(url))`, an uncached async IIFE, or
   `use(fetchData(url).then(...))` - the last one catches people even when fetchData IS cached,
   because `.then` returns a new Promise.

9. Wrapping `use` in try/catch. React throws internally to integrate with Suspense; the message
   even says "This is not a real error!". Use an error boundary.

10. A skeleton that is not the size of the content. Then it is a grey spinner and the layout still
    jumps.
