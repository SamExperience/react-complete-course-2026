MISCONCEPTIONS TO WATCH FOR, IN ORDER OF LIKELIHOOD

1. Testing implementation details - "the component calls useState twice", "the child got prop x".
   These fail on refactors that broke nothing. The sentence to repeat: test what it DOES, not how.

2. Using getBy to assert absence. It throws before the assertion runs, so the test can never pass.
   queryBy returns null and is the one for absence.

3. Using findBy for the loading state. By the time findBy resolves, loading is over - the test
   fails with the success DOM printed. Loading is synchronous: use getBy. The three async states
   need findBy.

4. Forgetting `await` on userEvent, or forgetting userEvent.setup(). Symptom: the assertion runs
   before the click has been processed.

5. Reaching for getByTestId immediately. Read the failure output first - it prints the DOM and the
   available roles, which usually names the query they wanted.

6. Writing tests that cannot fail: toBeDefined, typeof === "object", toEqual(itself),
   length >= 0. The question to ask: "what implementation would make this fail?"

7. Writing the no-mutation test as expect(result).not.toEqual(state). That compares the result
   with the input and says nothing about mutation. Assert on `state` itself, after the call.

8. Mocking a module with vi.mock as the first move. In this course the answer is almost always to
   pass the dependency in as a prop, which is a design improvement as well as a testing one.

9. Trying to run Vitest in the Jupyter notebook, or asking why the cells do not use it. The Deno
   kernel has no Vitest; the notebook builds a miniature runner to show what one is.
