MEASURED FACTS - do not contradict these, and do not "improve" the numbers

Experiment 28, one press of the App counter (StrictMode doubles every count; these are real
renders):
- App, PlainChild, Wrapper, PassedAsChildren, MemoObject, MemoCallback: 1 each
- MemoPrimitive: 0  (memo + an unchanged string prop)
Pressing the WRAPPER's own button: only Wrapper renders. PassedAsChildren renders 0 times,
because App created that element and App did not run.
Pressing a button that sets no state: nothing renders.
Adding `useMemo` to the object prop and `useCallback` to the function prop takes MemoObject and
MemoCallback to 0.

Experiment 29, typing "person-1" one character at a time, measuring only the time React blocked
the typing loop, three alternating repeats each:
- plain setQuery:               261, 274, 275 ms
- inside startTransition:       6, 6, 6 ms
And the finding that surprises people: with `Results` NOT memoized, the Transition mode renders
the expensive list TWICE per keystroke (16 renders for 8 keystrokes) against 8 in urgent mode,
because the urgent render re-renders the child with the old query first. With `memo`, both modes
do 8. A Transition and `memo` belong together.

Experiment 30: creating 50 rows takes under 1 ms; 5000 rows takes about 48 ms and leaves 5000 DOM
nodes. The lazy chunk is NOT requested until the button is pressed; the fallback shows, then the
component. The production build emits `30-lazy-child-*.js` at 0.42 kB beside a 221.90 kB main
bundle.

Notebook cell (L70): the same filter+sort averages 0.02 ms at 200 items, 0.07 at 1000, 0.33 at
5000, 2.18 at 20000, 7.38 at 50000 - so it crosses React's 1 ms guidance somewhere past 5000
items, which is far more than any screen displays.

AFTER THESE LESSONS THEY SHOULD BE ABLE TO ANSWER, IN PLAIN WORDS
- Why did this component re-render?  (its own state changed, or its parent rendered - props are
  not a cause)
- What does memo compare?  (each prop, by Object.is - so a fresh object or function defeats it)
- When is useMemo worth it?  (the calculation is measurably slow, or something downstream
  compares the identity)
- What does the compiler change?  (it writes the memoization; it does not diagnose, and it does
  not fix state living too high)
- What goes in a Transition?  (the expensive derived update - never the controlled input's own
  state)
- When do I split code?  (large, and plausibly never needed this session)

MISCONCEPTIONS TO WATCH FOR, IN ORDER OF LIKELIHOOD

1. Adding memo/useMemo/useCallback everywhere "to be safe". Ask what they measured. React's own
   answer to "should you add memo everywhere" is no.

2. Believing memo will stop a re-render when the prop is an object or arrow created in the
   parent's body. It will not, and experiment 28 shows it in one click.

3. Treating a high render count as a bug. Rendering is calling a function. A high count with a
   1 ms commit is not a problem; the Profiler decides, not the console.

4. Wrapping the text input's own state in a Transition. This is the one mistake that makes the
   app worse than before optimising. React forbids it explicitly.

5. Expecting a Transition alone to stop the expensive child re-rendering. Without memo it renders
   twice per keystroke. Point them at the measured numbers above.

6. Confusing debounce with a Transition. Debounce is about not sending eight requests; a
   Transition is about not blocking the main thread while rendering the results. A search box that
   hits the network usually wants both.

7. "React Compiler means I don't need to understand this." It writes the memoization; the
   diagnosis is still theirs, and it needs the Rules of React to hold.

8. Splitting a component that renders on first paint, or a 2 kB one. Both add a round trip and
   save nothing.

9. Reaching for windowing before trying "render fewer rows". Pagination is almost always the
   right first answer.
